# Rover commissioning checklist — 16 November 2026

This is a staged test plan, not an electrical release or a record of completed physical tests. Follow the unresolved gates in [FINAL_GO_NO_GO.md](FINAL_GO_NO_GO.md), [ENGINEERING_REVIEW_E2.md](ENGINEERING_REVIEW_E2.md), [ELECTRICAL_BLOCKERS.md](ELECTRICAL_BLOCKERS.md), and [CAMERA_WIRING.md](CAMERA_WIRING.md). Record instruments, actual values, component identities, reviewer and date for each physical result.

| Stage | Test | Acceptance and evidence |
|---|---|---|
| Software only | Main firmware | `.venv/bin/python scripts/verify.py`; build `esp32dev` from `src/main.cpp`, which includes `firmware/rover.ino`. Keep PlatformIO runs sequential. No upload occurs. |
| Software only | Laptop integration | `npm run sim:build`, `npm test`, `npm run build`, then `npm run test:e2e`. These exercise the C++ simulator and camera mocks; they cannot prove physical sensing, motor cutoff or video. |
| Unpowered inspection | Identify and trace hardware | Disconnect battery main/balance, USB and every supply. Verify actual DevKit, driver, sensor and camera variants, polarity, continuity, isolation, terminal maps, conductor/protection ratings and absence of power shorts. Resolve B01–B14 as applicable. |
| USB-only physical | Programming setup | Before any port opening/reset, confirm LiPo disconnected, motor/driver supplies disconnected, all unverified peripherals/power paths isolated, USB-only ESP32 power and no possible motor activation. Use the main DevKit, never the camera target. |
| USB-only physical | Bootloader communication | Enumerate the actual port; check both `cu` and `tty` owners. Read chip identification before flashing. If auto-reset fails, hold BOOT, press/release EN, wait one second, release BOOT; read using `--before no_reset`. Investigate corrupt/all-zero data before another attempt. Keep interlocks untouched. |
| USB-only physical | Main firmware upload | Obtain explicit approval immediately before `.venv/bin/pio run -e esp32dev -t upload --upload-port ACTUAL_PORT`. Preserve the uploader log and binary hash. Claim success only after tool success/verification. If a lower transfer rate is justified, use `upload_speed = 115200` under `[env:esp32dev]`, never `pio run --upload-speed`. Recheck frozen handover consistency after any configuration change. |
| USB-only physical | Main ESP32 startup | Capture actual ROM/startup output at 115200. Expect `READY DISARMED`, then `TEL ` JSON with `v:1`, `fw:"rover-usb-v1"`, `armed:false`, `auto:false`, requested/applied 0, `en:false`, brush/conveyor requests and outputs false. Expect a frame approximately every 500 ms. Validate with the repository protocol parser. Boot text alone does not identify the new firmware. |
| USB-only physical | Absent safety feedback and sensors | With the isolated GPIO27 feedback absent, expect `healthy:false`, `estop:true`, `nav:"ESTOP"` and every output disabled. With ECHO inputs isolated, no valid distance is guaranteed; inspect actual readings rather than assuming `-1`. Verify outputs stay disabled across multiple frames. Do not jumper GPIO27 or send RESET/ARM/AUTO/movement/cleaning activation. Telemetry is software state, not a voltage or motor measurement. |
| USB-only physical | Dashboard reception | `npm start` serves the built dashboard plus bridge on `http://127.0.0.1:8787`. Select Main ESP32 USB serial, refresh, select actual port, connect. The bridge sends only S/DISARM during this validation. Compare connection/protocol status, firmware, ranges/ages, disarmed state and E-stop state to raw serial. Do not click controls that activate outputs. |
| USB-only physical | Serial loss | While still USB-only and disarmed, disconnect USB and confirm dashboard loses protocol readiness, disables motion and clears telemetry. Reconnect deliberately; no automatic rearm or resumed movement. This is not a powered stopping-distance test. |
| Low-energy electrical | Supply and interfaces | Use a reviewed current-limited bench procedure with motors/battery disconnected. Identify and qualify buck/protection assemblies, 5 V/3.3 V limits, ripple, sequencing, backfeed and partial-power paths. Qualify U1/default-low networks and U2 powered-off isolation. Real 5 V ECHO must never connect directly to an ESP32 GPIO. |
| Low-energy electrical | Three ultrasonic sensors | After their protection is qualified, connect one sensor at a time: front TRIG/ECHO 32/34, left 33/35, right 13/36. Measure raw/conditioned HIGH/LOW, edges and overshoot; compare known targets and invalid/no-target behavior; test crosstalk and refresh age. Disconnect/change wiring only with all relevant power removed. Reboot disarmed and check disabled outputs with a sensor absent. |
| Low-energy electrical | Enable and physical E-stop | With motor branches isolated, scope GPIO14 and actual driver enables during reset, brownout and partial powering. Verify independent S2 interruption, K1 dropout, GPIO27 LOW on absent feedback, discharged motor bus and deliberate manual restart. Validate real contact ratings/terminal maps and release times. Do not force feedback HIGH or bypass any contact. |
| Motor-powered, separate approval | Left and right wheels | First resolve exact motor voltage/run/start/stall demand, summed two-motor driver limits, fuses/wires/connectors, recirculation, thermal limits and guards. Use an approved limited-energy procedure, wheels restrained/off ground as appropriate. Test left and right individually, then pairs; measure direction/current/temperature, reversal neutral interval, stop and physical E-stop. A passing GPIO test is insufficient. |
| Motor-powered, separate approval | Brushes | Verify combined M5+M6 demand on L298N channel A and total package thermal limits. Guard brushes, test at approved energy, record current/temperature and loaded stop. Both brushes share one command/channel. |
| Motor-powered, separate approval | Conveyor | Establish the actual conveyor voltage first. Qualify channel B with simultaneous brush load, diode/heatsink/connector ratings and protection. Guard the mechanism; measure current, delivery voltage, heat and stop. Firmware has no jam/current feedback. |
| Motor-powered, separate approval | Laptop manual control | After all prior gates pass, test explicit ARM then controlled press/hold/release, blur, browser loss, serial loss, deadman and physical cutoff. Manual drive has no automatic obstacle avoidance, rear/cliff sensing or encoder feedback. Measure the actual stopping distance. |
| Motor-powered, separate approval | Autonomous obstacle avoidance | Use a guarded area and independent physical stop. Verify front 35 cm, sides 20 cm, 45 cm recovery hysteresis, 180 ms settle, 100 ms neutral interval, timed turns and fresh three-sensor reassessment; persistent obstruction stops after three attempts. Test sensor faults/disconnection under a separately approved controlled procedure. AUTO has no laptop-link deadman and may continue after link loss. |
| Separate camera commissioning | ESP32-CAM and video | Identify AI-Thinker board/sensor/PSRAM and qualified programmer/supply before separate approval/upload. Preserve main firmware and GPIO mapping. Qualify the separate fused/protected camera branch and backfeed behavior. On trusted isolated WLAN, verify actual IP, `/status`, JPEG, MJPEG, settings, resource limits and loss/reconnect. Camera failure must remain independent of motor authority; camera mocks are not real video evidence. |

All motor/battery stages remain HOLD until wiring, ratings, protection and measurements are reviewed and the user explicitly approves that separate stage. Do not use the LiPo for initial load qualification.

The chip-ID failure seen on 16 November 2026 occurred before any flash write. A readable USB-adapter identity is not proof that the ESP32 bootloader responds. See [Espressif troubleshooting](https://docs.espressif.com/projects/esptool/en/latest/esp32/troubleshooting.html), [BOOT/EN procedure](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html), and [PlatformIO upload_speed](https://docs.platformio.org/en/latest/projectconf/sections/env/options/upload/upload_speed.html).
